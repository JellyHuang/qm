## Plain summary (15 lines)

1. Three features exist only as libraries with tests: the QM-side git MCP client and commit poller (`src/zq/git-mcp`), author mapping, and patch packages. Nothing calls them. `ZQ_GIT_MCP_URL`, `ZQ_GIT_MCP_SECRET` and `ZQ_GIT_AUTHOR_MAPPING` are parsed and then ignored.
2. "Wiring" means four concrete things: (a) a way for the agent to call the 9 git tools, (b) a scheduled poll of `check_updates` that feeds author mapping and then a notification, (c) an agent tool that builds a patch package, (d) retention and delivery of the package.
3. For (a), configuration alone does NOT work today. The registered-connector route is the right one, but the core refuses loopback addresses for MCP servers and the service binds only `127.0.0.1`. One of the two must change (small plugin setting, or an in-process agent tool).
4. The contract forces `check_updates` into the agent's tool list. An agent that echoes an `ack` could advance the stored branch tips and make the poller miss commits. Needs a guard.
5. For (b), the poller, the author mapper and a recording sink are tested; missing are the runtime function, the settings switches, the name-keyed author structure of phase 3b (the people directory adapter is needed only for the optional email fallback) and the real notification sink. Pattern to copy: the Jenkins poller (own function, own condition, lease key, sweeper).
6. For (c), the patch package builder needs a local git repository that holds the base commit. QM core has no clone and must not get the SSH key. This is a design gap that needs a spike before any code.
7. For (d), retention and delivery are now designed (`docs/zq-patch-package-phase4-design.md`, `docs/zq/patch-package-retention.md`) and the design is approved at design level (2026-11-17). The two tables `zq_patch_packages` and `zq_patch_deliveries` are NOT created and NOT enabled; creating them or switching anything on needs the PM's separate explicit consent plus a rollback plan.
8. Seven phases plus the sub-phases 3b and 4a to 4d (section 5A), each default-off behind its own switch, each with a staging check (steps, expected result, stop condition, rollback). The sub-phases live on their own branches, are never merged into `oa/dev` or `main` and are never deployed.
9. Rough effort: phase 1 about 4 to 10 hours, phase 2 8, phase 3 7, phase 3b about 57 (plus 3 for an optional import CLI), phase 4 8, 4a about 52 plus 8 to 10 for the builder input, 4b not separately estimated, 4c about 30, 4d about 12, phase 7 4; the old estimates of phases 5 (13) and 6 (20) are superseded.
10. Default-off proof for every phase: spies show no durable map requested, no sweeper created, no timer, no HTTP request, no agent tool offered.
11. Tables: none new before phase 3. Phase 3 and 3b create the two author tables in their NEW name-keyed shape (structure change approved at design level 2026-11-17; the old email-keyed shape is a historical note, not an execution basis). 4b and 4c create `zq_patch_packages` and `zq_patch_deliveries` (design approved, DDL text in sections 10 and 11 of the DDL proposal). None is created or enabled by an approval.
12. PM decisions: the author binding design (19) and patch package decisions 1 to 21 are DECIDED at design level, except one item that stays open as a pre-launch check: who tests on Windows and with real git-lfs (patch decision 5). Patch decision 7 (the GitLab push-rule answer for the `qm-bot@invalid` author) is void since the PM decided on 2026-11-17 that the applier is author and committer by default and that the commit goes on the current branch (`--new-branch` is the safe mode). Still to be supplied: the bot and external lists and the ignore list at deployment time (phase 3b), the Mattermost channel id and the owner map (phase 4), the ticket format (4a), the persistent retention directory and its backup (4b) and the verified upload limit (4c); section 6.
13. PR split: one small PR per phase, each through the merge queue with its Wall of shame report and a configuration and schema disclosure; the four existing branches are merged first as a separate step (see `docs/zq-git-mcp-staging-plan.md`). Phases 3b and 4a to 4d are the exception: they stay on their own branches, are not merged into `oa/dev` or `main`, and no PR is opened unless the PM says so (section 5A).
14. Nothing here touches production; every staging step is read-only toward GitLab.
15. Recommended first move: the PM chooses the agent-tool route (section 2), because it decides whether the plugin changes.

## 2. How the agent would call the 9 git tools

### 2.1 What the repo already allows by configuration

Admin MCP registration (`PUT /v1/admin/mcp-servers/<id>`, `src/api/routes/admin/mcp-servers.ts`, admin only) stores an `McpServer` record: url, `auth: "bearer"`, `bearerToken`, `readOnly`, `toolContract`, `attestActor`, `approval` (`annotations` default, `all`, `none`). `createMcpToolService` (`src/mcp/mcp-tool-service.ts`) lists the server's tools, checks them against `toolContract` at save and every refresh, and offers them to every scope's agents under the name `<serverId>_<tool>` (for example `zq-git_list_commits`). `docs/zq/gitlab-mcp-client.md` has the registration body. The same service object is what the zq runtime uses for OpenProject jobs (`call: (name, args, principalId) => mcpToolService.call(...)`, `src/wiring.ts:2666`). With `attestActor` the signed-in person goes to the service as `x-qm-actor`, which the service uses as the audit label.

So the agent can use the tools with configuration only, if the registration succeeds.

### 2.2 Two problems found

1. Loopback is refused. The connector fetch is `publicFetch` (`src/util/network.ts`, `createPublicFetch`): private addresses are refused unless the exact origin is in `PRIVATE_NETWORK_ALLOWED_ORIGINS`, and loopback, link-local and metadata addresses are refused even when listed ("which PRIVATE_NETWORK_ALLOWED_ORIGINS never allows"; the config parser rejects such an entry at startup). The registration example in `docs/zq/gitlab-mcp-client.md` uses `http://127.0.0.1:8765/mcp`. The service binds `127.0.0.1` hard-coded (`plugins/zq-git-mcp/src/service.ts:163`). As written, the registration cannot work. The poller's own client (`createGitMcpClient`) uses the MCP SDK transport directly, not `publicFetch`, so loopback works for jobs.
2. `check_updates` is exposed to agents. The contract requires exactly the nine names, so the registered server offers `check_updates` as well. It records first observations and, when given `ack` entries, advances the stored tips. An agent that passes an ack could make the poller skip commits. This is a state-changing tool offered through a `readOnly: true` registration.

## 3. Polling job: poller, author mapper, sink

Chain per tick (as tested today): `check_updates` -> batches -> `handle(batches)` -> only after success `check_updates` with `ack`, repeated up to 20 rounds. Failure of the handler means no ack, so the same commits return (at least once). The queue counts a sha once, so retries do not inflate counts.

Handler composition (new code only for the two bold parts):

1. poller (`createGitCommitPoller`, exists)
2. **runtime function** `createGitMcpRuntime(deps)` in `src/zq/git-mcp/runtime.ts`, same shape as the Jenkins one in `docs/zq-jenkins-wiring-options.md`: returns `undefined` unless its switch is on; takes `config`, `map`, `leaderLease`, `createSweeper`, `chat` pieces and `now`; wraps the sweeper in `leaderLease.hold("zq:git-mcp", ...)`; calls `client.verify()` at start and on each refresh and reports a contract violation as an error rather than polling.
3. author mapper (`createAuthorMapping(...).mapper.handle`, exists on the author-map branch in its email-keyed form; phase 3b makes it name-keyed with the order: person binding, ignore list, bot name rule, external domains, optional Mattermost email fallback, unmapped queue; the people directory from `createMattermostPeopleDirectory(chat.mmUserIdsOfEmail)` is then needed only for the optional fallback)
4. **sink**: phase 3 the recording sink; phase 4 a Mattermost sink that sends one DM per person (`chat.sendDm(mmUserIdOf(person))`) with repo, branch, sha and subject only, plus a digest of unmapped authors to the PM.

Where: `src/wiring.ts`, directly after the zq runtime is built (line 2688) and in the start and stop lists (3116, 3156). `createZqRuntime` is not touched.

## 4. Who consumes a patch package and how the agent asks for one

Consumer: the responsible person (a developer), who puts the package folder into the root of the repository and runs its `apply.sh` with no folder argument (or `apply.cmd`, `apply.ps1`; amendment 2 of `docs/zq-patch-package-phase4-design.md`), which applies the text part with `git am --3way --keep-cr`, adds any Git LFS files and makes one commit (the manual route is in the package READMEs, `README_CN.txt` and `README_EN.txt`). QM never pushes and never opens a merge request. The decided delivery channel is a Mattermost direct message with the zip attached; the recipient rule is DECIDED (2026-11-17, decision 13): the requester by default, the base commit author through the author binding only when chosen.

Agent request: a tool `zq_patch_package` with arguments `repo`, `base` (full commit id), `paths`, `ticket`, `subject`, `body`, and for spreadsheets the workbook the agent produced. It follows the `zq_add_child_orders` pattern: tool in `src/agent/agent-tools/`, a `ToolContext` method, a service function, offered only when the switch is on and the turn is not read-only. The tool (sub-phase 4d) never delivers by itself: it builds the package, records the resolved recipient and answers with the manifest summary; delivery is sub-phase 4c. Text changes use `fetchCompleteDiff` to read a diff with explicit paths (refused if one file is longer than one response), or a working copy; spreadsheets use `xlsxPager` plus the modified file.

Design gap, found by reading `text.ts`: `buildTextPatchPackage` needs `repoDir`, a local repository that contains `baseCommit`; the scratch repositories borrow objects through alternates, with no remote and `GIT_ALLOW_PROTOCOL=none`. The service holds blobless clones that cannot serve blobs offline, and the SSH key must never reach QM. Options for the spike (phase 4a, first step): (a) build the base files of the touched paths from `read_file` into a small scratch repository and apply the diff to that, so no clone is needed (preferred, needs a new builder input); (b) a read-only deploy key on a QM-side clone (breaks the "key only in the service" rule); (c) build inside the service as a tenth tool (breaks the nine-tool contract). The choice affects the plugin and the contract, so it is a PM and design decision. The spike (the first step of 4a) is written up in `docs/zq-patch-package-repo-source.md` (recommends option (a), with a local experiment and the decisions it needs).

## 5. Phases, estimates, risks and staging checks

Every phase is merged with its switch off. "Default-off test" lists the spies that must show nothing happens; they are written first and must fail on a version that wires unconditionally. Staging is always read-only toward GitLab.

### Phase 1: agent access to the read tools (route B chosen by the reviewer on 2026-11-17, to be confirmed by the PM)

Decision note: `docs/zq/git-mcp-agent-access.md` on `oa/zq-wire-1-access`. Route A+C (connector registration, plugin bind address, guard) was set aside: it widens the network exposure, offers `check_updates` to agents and needs a new field on the persisted MCP server record. It stays available as a later switch.

- Work (done on `oa/zq-wire-1-access`): the in-process tool `zq_git` with an `operation` field and eight read operations, strict per-operation argument schemas, a `ToolContext` method `callZqGit`, `ZQ_GIT_AGENT`, contract check on first use and every five minutes, caller label per person. No change to the plugin, to `src/util/network.ts`, to the MCP server record or to the admin API. A smoke script, `scripts/zq-git-agent-smoke.ts`, is on the same branch.
- Service-side protection: none in route B. `check_updates` is kept from the agent only by core's fixed operation list and input validation; the plugin's caller label guard for `ack` is not implemented, so a holder of the shared secret can still call it directly.
- Switch: `ZQ_GIT_AGENT=1`, only with `ZQ_GIT_MCP_URL` and `ZQ_GIT_MCP_SECRET` both set; without them startup fails with a clear message. URL and secret alone enable nothing. No tables in QM.
- Default-off test: with the switch off the agent tool list has no `zq_git` tool (also in read-only turns), nothing is built and the fake service sees zero requests.
- Staging check (route B, read-only toward GitLab): see section 10.

### Phase 2: poll in dry-run (about 8 hours)

- Work: `createGitMcpRuntime`, config switch, wiring, handler that logs counts only, verify at start and refresh. Tests: fake service with the real client (the existing poller test pattern). Risk: double polling in a blue-green deploy, covered by the lease key `zq:git-mcp`; a handler that throws blocks the ack by design.
- Default-off test: with only URL and secret set, the fake service sees zero requests, no sweeper is created, no map requested. With `ZQ_GIT_POLL=1` only: one sweeper, requests to the fake service only, no map requested (this phase creates no table in QM).
- Staging check: set the switch with the service on memory stores. Expect: the first poll records baselines and reports nothing; the journal shows counts; a second poll reports `unchanged`. To see commits, move one stored tip back in the staging database as described in the service handoff (step 7), and expect the commits once, then none after the ack. Stop on: any error line of kind `unreachable` that repeats, contract violation, or the same commits delivered twice after an ack. Rollback: unset `ZQ_GIT_POLL`; the service state stays valid.

Implemented on `oa/zq-wire-2-poll` (independent of phase 1, based on `oa/zq-git-mcp`); description in `docs/zq/git-mcp-poll.md` there.
