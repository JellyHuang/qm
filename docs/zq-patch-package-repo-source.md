# Spike: where the patch package gets its local repository

Status: design only, no code. Written for the first step of sub-phase 4a (the patch builder) of `docs/zq-git-mcp-wiring-plan.md` (formerly phase 5) (section 4, "Design gap"). Nothing is deployed and nothing was changed outside this document.

## The gap

`buildTextPatchPackage` (patch-package branch) needs `repoDir`, a local repository that contains `baseCommit`. QM core has no clone, and the SSH key lives only in the git MCP service's account. The service's clones are blobless and fetch blobs on demand through a temporary bare `GIT_DIR` with alternates; it never writes to the remote. The question is how the builder gets base objects without the key reaching core.

## Experiment for option B (run for real, outside the repo, removed afterwards)

Claim under test: blob ids depend only on content, so a scratch repository built from the real base contents has the real base blob ids, and its patch applies with `git am --3way --keep-cr` to a real clone.

Commands (all in a `mktemp -d` directory, with `GIT_CONFIG_GLOBAL=/dev/null`, git 2.52.0):

```
git init -q -b main origin                      # real repo: a.txt (40 lines), crlf.txt (CRLF), bin.dat (20000 random bytes),
                                                # old_name.txt (61 lines), book.xlsx (zip), other.txt; one commit B
git clone -q origin real; git -C real checkout -q B
git init -q -b main scratch                     # scratch: ONLY the touched paths, base bytes taken with `git show B:<path>`
git -C scratch add -A; git -C scratch commit -qm synthetic-root
git hash-object <file>   vs   git -C origin rev-parse B:<file>
# edit in scratch: a.txt line 20, crlf.txt line 2, bin.dat replaced (25000 bytes), git mv old_name.txt new_name.txt + one line, book.xlsx replaced
git -C scratch commit -qam "Fix things"
git -C scratch format-patch -1 --binary --full-index --no-signature -M -o ../pkg
git -C <fresh clone at B> am --3way --keep-cr ../pkg/0001-Fix-things.patch
```

Results:

| Check                                                                                                     | Result                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blob ids of scratch base files vs the real base commit (5 files: text, CRLF, binary, xlsx, rename source) | All five identical. The `index <old>..<new>` lines of the patch carry the real base blob ids.                                                                         |
| `git am --3way --keep-cr` on a clone at B                                                                 | Applies cleanly (text, CRLF, binary, xlsx, rename detected as `old_name.txt => new_name.txt`). Resulting blob ids of all five touched paths equal the scratch result. |
| plain `git am --keep-cr` (no 3way) on a clone at B                                                        | Applies cleanly.                                                                                                                                                      |
| `git am` without `--keep-cr` (with or without `--3way`) on the CRLF file                                  | "Patch failed". `--keep-cr` is mandatory when a touched file has CRLF (the doc of the library already says so).                                                       |
| Target branch moved on (unrelated commit on a.txt line 5 and other.txt), `--3way`                         | Applies, result has both the other commit's line and the patch's line. Plain `am` also applied (hunks have enough context).                                           |
| Target changed the same line the patch changes, `--3way`                                                  | "Patch failed" with conflict markers left for the developer: the correct outcome, and 3way could use the real base blobs for it.                                      |
| Base bytes not exact (CRLF base turned into LF, as a lossy text read would do)                            | Blob id differs (`83db48f8...` vs real `b87108ab...`), the patch fails even with `--3way`: no real base blob to merge against, and the context lines have no CR.      |
| `index` lines deleted from a patch containing a binary file                                               | Fails ("bad git-diff"): binary patches need the index line. Text-only patch without `index` lines applied, with and without `--3way`, on a clean and a moved base.    |

Conclusion for B: the reasoning holds. Provided the base bytes are exact, no key and no clone are needed, `--3way` works against the developer's real repository (the needed base blobs are in it), and the patch is byte-equivalent to what a real clone would produce. The condition is byte-exactness of what core receives. The experiment did not test whether `read_file` returns exact bytes: its text kind returns `content` with `cutChars`, and the binary kind returns base64 only on request in ranges. That must be checked against the plugin before choosing B (see decisions).

## Recommendation

B, with a hard condition: verify that `read_file` returns exact bytes (text and binary) first; if it does not, add an exact-bytes mode to the service (a small, read-only change to an existing tool, not a tenth tool). B keeps the key in the service, touches neither the nine-tool contract nor the write-name rules, and the experiment shows the patch is equivalent to one built from a real clone, including binary, xlsx, rename and `--3way` against a moved target. Keep A as the fallback if the PM sets no size cap and files are large (hundreds of MB), and D as the interim answer until the agent tool (sub-phase 4d) ships. C is not recommended: it adds a second key custody for no capability that B lacks.

Builder change for B (design only): replace `repoDir` with an input `baseFiles: { path, bytes | file }[]` plus `baseCommit` (recorded in the manifest, not used to look anything up), build the synthetic root commit from those files, commit the new files on top, `format-patch --binary --full-index --no-signature -M`, then verify by `git am --3way --keep-cr` onto a second scratch built from the same base files. The commit message trailers and the manifest stay unchanged; the manifest should state `source: "base-files"`.

Honest limit of the verification in B: the library's own `git am` check proves the patch applies to the scratch base, which equals the real base only if the bytes were exact. The real check is a comparison of `git hash-object` of each received base file with the blob id the service reports (`read_file` already returns `oid` and `sha256` for binary; the text kind must return its blob id too, or core computes `sha256` and the service confirms it). That exactness check is part of B's cost above.

## PM decisions needed before phases 4 and 5

Phase 4 is live notification and does not depend on this spike; its decisions are in section 6 of the wiring plan (channel id, who "the PM" is, wording, owner map). Decisions that this spike adds, all before sub-phase 4a:

1. Route: B (recommended), A or D. If A, also accept a tenth tool and its name.
2. Size cap for one package (total base plus modified bytes, and per file), and what happens above it (refuse and answer with D's instructions, or allow a streaming route in A).
3. Whether a small, read-only change to the git MCP service is acceptable now (exact-bytes `read_file`, blob id on text results), since it changes the plugin and its contract version.
4. Whether xlsx packages stay on the `diff_xlsx` table plus the workbook as delivered (no patch), which needs none of this.
5. Recipient rule and ticket format (already open in section 6), since they affect the patch text and the manifest.
6. Who runs the exactness check and what the tool does when it fails (refuse; no package is better than a wrong patch).
7. Whether the interim answer D is wanted if sub-phase 4d is delayed.

## Not verified

- That `read_file` returns exact bytes for text with CRLF, lone CR, non-UTF-8 bytes or a BOM, and that binary base64 ranges can be reassembled of a file larger than one response. Only the git side was tested.
- Time estimates are judgment, not measurement.
- Nothing was run against the real git MCP service, a real remote or the real repositories; the experiment used invented files.
