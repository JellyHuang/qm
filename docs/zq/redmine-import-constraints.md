# Redmine import: constraints on the QM side

The importer lives with OpenProject. These are the rules QM needs while it runs and the order in which QM is turned on afterwards.

## Before and during the import

1. Every ZQ switch stays unset on the QM instance that reads the target OpenProject: `ZQ_SCANNER`, `ZQ_REMINDER_DELIVERY`, `ZQ_REPORTS`, `ZQ_CHANGE_DIGEST`, `ZQ_FEATURE_CHANNELS`, `ZQ_CHILD_ORDERS`, `ZQ_ROLEPLAY_MM_USER`, `ZQ_ROLEPLAY_PROJECTS`. Nothing reads or writes OpenProject while the import runs.
2. The importer sends no mail or notification (OpenProject side).
3. Imported history is written as readable activity notes, never as whole source documents, so the change feed carries nothing QM could mistake for a new change.

## Why no cursor reset is needed on a fresh QM

QM stores a change-feed cursor per project and person only when `ZQ_CHANGE_DIGEST` is on. The first read of a project has no cursor: QM saves the cursor and ingests no events, so everything imported before that first read is history, not news. Likewise a feature seen for the first time only records a snapshot; lines appear for later changes only. A cursor reset is needed only if the change digest ran before the import: delete the project's rows in `zq_change_cursors` (key `<projectId>:<principalId>`) or let the server answer `cursor_invalid` / `cursor_scope_changed`, which QM treats as a resync that drops the old events.

## Turning QM on after the import (nothing here is done yet)

1. **Key table.** Install the production key table first: `optimizationType`, the people fields (`planner` list, `participants`, `reviewer` as the producer), the completion properties (`delivery_result`, `delivery_submitted_at`), and `stageOwners` for the planning-acceptance stage addressed to `field:responsiblePlanner`. Without it QM reads the wrong or no owners.
2. **Identity links.** Only people with a confirmed OpenProject↔Mattermost link can be scanned; the scan runs as one of them. Unlinked users are counted as `unlinked` and receive nothing.
3. **Dry run.** Set `ZQ_SCANNER=1` with `ZQ_REMINDER_DELIVERY` unset. Reminders are recorded, not sent. Read the scan report: `featuresSeen`, `created`, `ceilingHit`, `noHolder`, `unlinked`, `unsetResponsibility`, `contractProblems`. A large `created` is expected: the whole open backlog counts as new on the first scan.
   `ZQ_RECIPIENT_ALLOWLIST` (comma-separated Mattermost user ids, empty by default = no limit) restricts every recipient QM picks: unlisted people are never scheduled a reminder, never added to a feature group, never sent a card, and a send to an unlisted id is refused. Use it for the first live phase (one person) and widen it only on the owner's say-so.
   `ZQ_MORNING_AT=09:30` (unset = off; needs `ZQ_SCANNER=1` and `ZQ_REMINDER_DELIVERY=1`) sends each linked person, on weekdays at that Shanghai time, one message with their own orders: not started, running, and, once an order is handed in, the lowest-numbered waiting order as the next one. A person with no orders gets nothing. It respects `ZQ_RECIPIENT_ALLOWLIST`.
   `ZQ_DAILY_ASK_AT=17:30` (unset = off; same prerequisites, same allowlist) asks each linked person on weekdays what they did today. Their first direct message afterwards is kept as the daily reply (stored in `zq_daily`, keyed `<mattermost user>:<day>`) and is not passed on to the assistant; later messages are ordinary again. Orders of theirs named by number (`#12`, `OP12`) or by a title of three or more characters get a card asking whether the order is done. Yes or no is only recorded: the answer tells them to change the status in OpenProject themselves, QM never writes it.
   `ZQ_BIND_CARDS=1` (off by default; needs `ZQ_IDENTITY_MAP=1` and `ZQ_BIND_CANDIDATES_FILE`) sends each person in the candidates file one identity card: the OpenProject name and login, and their Mattermost account, with the buttons 是我 and 不是我. The file is a JSON array of `{mmUserId, opUserId, opLogin, opName, mmName?}` prepared by the operator (matching by email stays outside QM) and lives where the container can read it, for example `/data/zq/`. Only people `ZQ_RECIPIENT_ALLOWLIST` permits are asked, and nothing is recorded for the others, so they are asked once the allowlist widens. Only the person themselves can answer: 是我 links the accounts, 不是我 records `declined` (the person is not asked again) and sends one message to `ZQ_BIND_NOTIFY_MM_USER` when it is set. `POST /v1/admin/zq/identity-links/:mmUserId/resend` asks again (it drops the old record first), and the existing `DELETE` on the same path unlinks. Identity links keep their table; the only change is two new values, `status: "declined"` and `source: "card"`, and an optional `declinedAt`. `ZQ_WEEKLY_BRIEF_AT=09:00` (unset = off; same prerequisites; Wednesday, Shanghai time) sends each trade lead a brief of the open orders of their trades. Leads come from `weeklyLeads` (section title to users, an optional override that wins) or else from `typeLeads`; a trade without either goes to `defaultLead` (the draft key table sends the planning, numbers and Other sections to Zhou Olivia, OP user 62, through `weeklyLeads`; the producer gets no weekly brief). Sections are named by `weeklyLabels` (type key to section title); a type without a label goes into a last section named `其他`. Inside a section the orders are grouped under `【parent feature title】` (an optimization order without a feature under `【(没有上级总单)】`) and numbered through the section. The first line is the Friday-to-Thursday week that contains the send day. Each line is `name percent status`, the percent is the work package's `percentage_done` (also read as `done_ratio` or `percent_complete`) and is replaced by `(未取到完成百分比)` when OpenProject does not return one; a delayed order or an awaiting note adds `(备注:…)`. Done, closed and suspended orders are left out. Only leads who may be written to (`ZQ_RECIPIENT_ALLOWLIST`) get a brief.
4. **Role-play pass.** Set `ZQ_ROLEPLAY_MM_USER` and `ZQ_ROLEPLAY_PROJECTS` and turn delivery on: every message goes to the tester only, each stating who it was meant for and which rule fired. Run `scripts/zq-roleplay-report.ts` for a readable list first. Reset with `roleplayReset()` before the real run.
5. **Real run, in this order, one switch at a time:** reminders to a small set of people first (the daily ceiling `ZQ_REMINDER_DAILY_CEILING`, default 200 per person, caps a flood), then the change digest and feature groups, then reports. Each step needs the operator's explicit go.

## Identity

Accounts without a link receive nothing and are reported as `unlinked`. OpenProject users created without an email cannot be linked by email; link them by hand.

## Database change for the daily question

`ZQ_DAILY_ASK_AT` is the only switch that opens the `zq_daily` map, so with it unset nothing below happens.

- **Migration:** none by hand. The first time the map is opened, the same durable-map migrations that create every `zq_*` table run at startup: `CREATE TABLE IF NOT EXISTS zq_daily (id TEXT PRIMARY KEY, json JSONB NOT NULL)`, a row in `durable_map_versions`, then the tenant column and the two claim functions `claim_zq_daily` and `claim_zq_daily_tenants`. All of it is additive and idempotent.
- **Rollback:** turn `ZQ_DAILY_ASK_AT` off and redeploy the previous build. The old build never opens the table, so the table can stay. To remove it entirely afterwards (it only holds daily replies): `DROP TABLE zq_daily; DROP FUNCTION claim_zq_daily(); DROP FUNCTION claim_zq_daily_tenants(); DELETE FROM durable_map_versions WHERE tbl = 'zq_daily';`. Run it only after the previous build is serving, and take a dump first if the replies matter.
- **Not affected:** `zq_reminders` gains an optional `batch` JSON field on new rows only; old rows and old builds read it fine.
