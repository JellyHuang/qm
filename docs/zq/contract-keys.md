# Contract key table

QM reads stage, lifecycle and duty keys from one JSON file named by `ZQ_CONTRACT_FILE`. OpenProject owns it and fills it in; QM matches on the keys and never on Chinese display names. `test/fixtures/zq-contract-keys.json` is the shape with draft values.

| Key                             | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`                       | Version of the table; bump it when a key changes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `featureType`                   | `type_key` of the 功能总单                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `optimizationType`              | Optional. `type_key` of the 优化单, which exists in two forms: under a feature it is one of that feature's orders (its child orders are read with the feature, its reminders go to its own planner or else the feature's planner, and it reports to the feature's PM); with no feature parent it is scanned on its own and needs its own planner and PM fields. One with no feature parent is scanned like a feature: unassigned and overdue reminders, and a reminder to the planner once all its child orders are done. The executor of a single-person order submits a completion confirmation (`fields.completionSubmitted`, default `completion_submitted`; the order counts as submitted when the property is `true` or the string `pass`, which is what OpenProject's `delivery_result` carries) and the stage stays in progress; QM then asks the planner once to accept it. Only the planner moves the order to done. When the order also carries a submission time (`fields.completionSubmittedAt`, default `delivery_submitted_at`, a date-time), every new submission time is reminded once, so a re-submission after a return asks the planner again; without it the planner is asked once per order. It reuses the order stages; it has no QA stage and no plan-date rule |

Lifecycle keys are fixed: `normal`, `suspended`, `cancelled` (`delayed` is still read for the 0.3.1 table; in 0.4 the delay is the separate `delay_marked` flag).

## What QM reads from `zq_list_work_packages`

Called with `{ limit: 100, offset }` and paged by `next_offset` until it is `null` (`total` is never trusted). QM reads each normalized object (`stage_key` is the stage; `status_key` is a same-value alias used when `stage_key` is missing; if both are present and differ, that order is skipped and reported as a contract problem): `{ id, subject, project_id, type_key, stage_key (falls back to status_key), lifecycle, parent_id, assignee: {id, login, name, type} | null, due_date, status_changed_at?, <fields.*> }`. `fields` names the properties for the responsible planner (`{id, login, name} | null`), the estimate (hours, or an ISO 8601 duration), and the planned start and end. A date without a time is a Shanghai calendar day: it ends at 23:59:59.999 +08:00. An assignee whose `type` is not `User` (a group) does not count as a person assigned. An error comes back as `{ error: { code, message } }`; `not_found` on an optional tool means the feature is not visible and the answer is left out, any other code fails that person's scan.

## Optional tools

- `tools.exitCheck`, called with `{ id }`: `{ ready: boolean, blockers: [{ code, message }] }`.
- `tools.meetingsForFeature`, called with `{ id }` and paged by `next_offset`: `{ results: [{ id, title, end_time, state }] }`; `state` is `draft | open | in_progress | closed | cancelled`.
- `tools.bugsForFeature`, called with `{ id, offset }` and paged: `{ results: [normalized bug with blocking, assignee, qa_owner] }`.
- `tools.changesSince`, called with `{ project_id, cursor, limit }`: `{ results: [event], next_cursor, has_more }`; each event has `event_id`, `ticket_id`, `parent_feature_id`, `kinds`, `old`/`new`, `actor`, `occurred_at`, `reason`, `batch_id`.
- `tools.dutyHolders`, called with `{ project_id, duty }` and paged: `{ results: [{ id, login, name }] }`; empty means nobody holds the duty, several means several.

## People fields

`fields.responsiblePlanner` may hold several users; every one of them gets what is addressed to the planner, and the first is the main one in digests and roles. `fields.participants` (default `participants`, a list of users; shown as the developers, derived by OpenProject from the executors of the feature's live orders) is, with all the planners and the producer, the membership of the feature group; QM no longer adds the order executors itself. `reviewer` is the producer who reviews the plan. The acceptance stage is addressed to the planner through `stageOwners`; QM no longer needs a separate acceptor or regression owner, and those two keys stay readable only for key tables that still name them.

A feature with responsible planners but no assignee asks its producer (`reviewer`) once which planner takes it as the assignee; a different set of planners asks again. QM never picks the assignee itself. The feature is not asked while it is finished: its stage is `stageRoles.featureDone` (optional) or OpenProject marks it closed (`is_closed` or `isClosed` on the work package). QM does not read any separate "owner" property: the assignee is the one who handles the order.

## Who is asked for an order nobody holds

`typeLeads` (optional) maps a type key to the people who answer for it: `{ "backend": [{ "id": "12", "name": "…" }] }`. An unassigned order of that type, an unassigned optimization order (`optimization`) and an unassigned bug (`bug`, rule `bug-unassigned`) are addressed to those people. A type with no entry falls back to the duty holders for its type (the planner for an optimization order), and when there are none, to `defaultLead`.

`defaultLead` (optional, one `{ "id", "name" }` user, empty by default) is addressed by every "nobody is assigned" reminder that finds no lead: an unmapped type, no duty holder, an unassigned bug of a type with no lead. QM only reminds; it never picks an assignee. A feature without an assignee is still addressed to its producer.

The draft in `test/fixtures/zq-contract-keys.json` maps art types (character/scene concept and model, level art, animation) to 闫文 (45), `vfx` to 朱升 (29), `frontend` to 朱毅 (35), `backend` to 栋黄 (5), `qa_test` to 林凯 (38), `ui` and `fgui` to 胡西尧 (41), and `defaultLead` to 栋黄 (5). The `qa_test`, `ui` and `fgui` entries are a draft from the OP role holders, not yet confirmed by jelly.

## Empty responsibility fields

A person field named by `stageOwners` that is empty on the feature is never replaced by a duty group. QM sends no reminder for it and instead emits `responsibility-not-set` to the duties in `ZQ_UNSET_RESPONSIBILITY_DUTIES` (none by default, so it is only counted in the scan report).

`stageRoles.taskActive` (optional) names the execution stage that means "being executed", for example `execution.active`. An assigned order in that stage that has no start date or no expected end date (`due_date`) is asked for the missing one once (`task-dates-missing`); it is never asked while waiting, unassigned or done. Without the key the rule is off.
