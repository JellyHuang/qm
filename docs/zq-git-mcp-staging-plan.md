## Summary for the PM (plain language)

1. The four branches can be combined. The only real conflicts are small and mechanical: one file with settings (`src/zq/config.ts`) and a few old git files that a newer commit on `oa/dev` touched. I resolved them in a trial; the combined code compiles, passes lint and every test that does not need a database (plugin: 234 pass, core zq: 216 pass, 0 fail).

Four things are NOT finished and block a real staging run of the full flow: (a) no migration creates the two tables `zq_git_branch_tips` and `zq_git_blob_meta` yet; (b) the QM-side git client, the author mapping and the patch package are not wired into QM at all, so switching them on does nothing; (c) the plugin has no CI job; (d) two exports make `knip` fail (a two-line fix).
6. What you (PM and operations) must supply: a dedicated read-only GitLab deploy key limited to the 7 repositories, the database role and tenant uuid, the secrets, a host with git 2.44 or newer, the Mattermost channel id and owner map for Jenkins notices, the ticket id format and the company email domains. 7. Not verified yet: Postgres with row level security, real Mattermost delivery, real Jenkins reruns, and the full core test suite with a database (this environment has no Postgres).
8. Nothing may be deployed before you give written approval together with a rollback plan (section 8 lists the rollback points).

## 3. Recommended order, method and history

### 3.1 Order

1. `oa/zq-git-mcp` (base of the other three; carries the removal commit and the plugin).
2. `oa/zq-author-map` (clean; builds on `src/zq/git-mcp/authors.ts` of the base).
3. `oa/zq-patch-package` (one conflict hunk in `config.ts`; depends on the git-mcp client types only).
4. `oa/zq-jenkins-rerun` (last: the only branch that changes runtime wiring, three conflict hunks in `config.ts`, and the most behavioural risk; landing it last makes it a single revertable merge on a known base).
5. Docs from `oa/spike-git`: bring `docs/zq-git-mcp-ddl-proposal.md` and `scripts/zq-git-mcp-real-it.sh` (the plugin docs reference that wrapper) as one docs commit with `git checkout origin/oa/spike-git -- <paths>`. The other spike scripts are exploratory ("not part of the build"); the full branch merges cleanly too (no overlapping files) if the PM wants the history, but there is no need to ship it into the release.
6. Then the fixes from section 2 (the two `export`s, the migration for the two plugin tables, the example env) as small commits on top, so review of each merge stays a pure merge.

Other orders also work (the conflicts are only in `config.ts`; jenkins-first then author-map conflicts in the same file), so the order above is chosen by risk, not by necessity.

### 3.2 Merge, not rebase, not squash

- `git merge --no-ff` for each branch into the staging branch (cut from `origin/oa/dev` tip `5c1e25845`). A rebase would rewrite `7f8eab470` and every SHA that the docs cite (`7f8eab470`, `dd20bf0ad`, `fba6d5260`, `0e340d90a`, `cd2546ed0`, `0f5fd6543`), and the docs' rollback instructions would point at nothing.
- A squash would erase the isolated removal commit, which is the rollback point. Do not squash any of these PRs.
- Record the conflict resolutions in the merge commit messages (which file, which side) so a reviewer can read them without redoing the merge.
- Tag the pre-merge tip (`git tag staging-base 5c1e25845`, local convention, push the tag to origin only, never to upstream) and the tip after each merge, so the section 8 rollbacks have names.
- Commit rules: no AI attribution or coauthor trailers on any commit (the `coauthor-trailers` CI job rejects them on new commits); no comments in code files (the branches already follow this; the merged `config.ts` resolution adds none).

### 3.3 How this lands in the repository

The repository rule: PRs land through the merge queue (`gh pr merge <n>` queues; never `--admin`). This repository is a downstream fork, so every `gh` command takes `--repo JellyHuang/qm`, and nothing is opened against the upstream repository (and no upstream issue or PR number appears in any commit, PR text or comment).

Options, in order of preference:

1. Four PRs, one per feature branch, landing in the order above into a long-lived staging branch (for example `oa/zq-staging`, created from `oa/dev`). Each PR is reviewable on its own and each lands as a merge commit. The merge queue's merge method for that branch must be "merge commit" (repository setting or ruleset for the base branch).
2. If the queue can only squash or rebase, split the removal into its own PR containing exactly the commit `7f8eab470` (a cherry-pick keeps the one logical change; the squash commit then is the rollback point) and give up the SHA references in the docs; update those docs in the same PR.

Each PR needs the "Wall of shame" report in the description (see 3.5) and, because the change set is a mix of backend behaviour with no UI, no screenshots; the live dev-instance QA rule (Slack in Firefox) applies to the Jenkins notice path and the Mattermost author notices, which cannot be reached without a Mattermost surface and a Jenkins; record "not run, reason" honestly in the PR rather than skipping silently.

### 3.5 Wall of shame report for the later PRs

`CLAUDE.md` and `.github/workflows/wall-of-shame.yml` require, in every PR description, a review report that covers every lens of `docs/SPEC.md` for the PR head commit. Steps: (1) triage the diff with the latest Haiku against all lenses in the spec; (2) the lenses marked always reviewed (Overengineering, Band-aid fixes, Duplication, Hand-rolling, Non-durability, Config-matrix expansion, Historylessness) always get a fresh independent reviewer, the other relevant lenses get one each; (3) each reviewer returns accept or request changes, a score out of 100 and 1-2 sentences, and the description lists reviewer, lens, verdict, score, assessment and the reviewed commit; (4) lenses judged not relevant are listed as `Not relevant` with the triage model as reviewer and its one-line reason; (5) update after every push, and re-review affected lenses. The CI check fails until all lenses are covered for the head commit. Lenses that will certainly matter here: Non-durability (author queue, Jenkins state, audit are in Postgres; the in-memory recording sink is for tests and dry-run only), Config-matrix expansion (about 30 new settings, section 4, plus about 11 author binding and 10 patch package settings of the later sub-phases, all default off), Duplication (the author resolver and the Jenkins store reuse `pruneGitAudit`; check the plugin's own local helpers against `plugins/chassis`), Historylessness (the removal of `src/zq/git/*` must say why in the PR text), Band-aid fixes, Arbitrary limits (caps and timeouts in the plugin, all documented with source).

Also disclose in each PR description (repository rules): added and removed settings with defaults (section 4), and the schema section: for the tables of sections 8 and 9 of the DDL doc and the three plugin tables, give old and new shapes, keys, indexes, constraints, JSON fields and representative rows. The DDL doc already has them; copy them, label invented examples, and state "no existing table, column, index, constraint or JSON key changes" (the doc's own statement).

### 6.4 Approval gates
